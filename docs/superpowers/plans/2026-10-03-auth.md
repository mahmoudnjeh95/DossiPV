# Auth & Accounts Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Build `@dossipv/auth`: bcrypt password hashing, login/logout/session-validation for
company users (with the per-company concurrent-session anti-sharing cap) and the super-admin
(separate table, no cap), plus in-memory per-email rate limiting on login attempts.

**Architecture:** A new workspace package depending on `@dossipv/db` and `bcrypt`, following
the monorepo's established per-concern package pattern. One `@dossipv/db` schema migration
(adding `SuperAdminSession`) precedes the auth logic itself. Every exported function is a
plain async function taking/returning plain values — no framework coupling (no Next.js
`Request`/`Response`/cookie APIs inside this package; `apps/web`'s own route handlers own
that translation layer in a later sub-project). Tests run against the real tunneled dev
database (same philosophy as `@dossipv/db`'s own seed script — no mocking Prisma), each test
creating and cleaning up its own throwaway rows.

**Tech Stack:** `bcrypt` 6.0 (verified installs and runs cleanly on this Windows dev machine
with prebuilt binaries — no native-build issues found; `@types/bcrypt` 6.0 for typings),
`@dossipv/db` (Prisma Postgres client), Vitest, Node's `crypto.randomBytes`/`createHash` for
session tokens.

**Spec:** `docs/superpowers/specs/2026-10-03-auth-design.md`

## Global Constraints

- `@dossipv/auth` depends on `@dossipv/db` only (plus `bcrypt`) — it does not depend on
  `apps/web`, and nothing in `@dossipv/db`, `@dossipv/engine`, `@dossipv/document-text`, or
  `@dossipv/dossier-worker` gains a dependency on `@dossipv/auth`. Matches the existing
  dependency-direction discipline established across all prior sub-projects.
- The SSH tunnel to Postgres (`ssh -f -N -L 5433:127.0.0.1:5433 dossipv-server`) must be alive
  for every task in this plan — every test hits the real database. Check at the start of each
  task, not just once at the start of the plan, since tunnels can drop mid-session.
- No framework/cookie code in `@dossipv/auth` itself (see spec §3's note) — every function
  takes/returns plain strings and plain objects, never a `Request`/`Response`/cookie object.
  This is a hard boundary, not a style preference: a later sub-project (#4, the web UI) is the
  only place Next.js-specific cookie-setting code may live.
- Session tokens: raw token is `crypto.randomBytes(32).toString('hex')` (64 hex chars);
  stored value is `crypto.createHash('sha256').update(rawToken).digest('hex')` — never store
  or log the raw token anywhere outside the value actually returned to the caller of
  `login()`/`loginSuperAdmin()`.
- `InvalidCredentialsError` must be thrown identically (same type, same message) whether the
  email doesn't exist or the password is wrong — this is a stated security property from the
  spec (§3), not an implementation detail; a test must assert this explicitly (see Review
  Focus).
- Rate limiting is in-process memory (a module-level `Map`), explicitly not persisted or
  shared across instances — this is a documented, accepted limitation (spec §2), not a bug to
  silently "fix" by reaching for Redis or similar during this plan.

## Review Focus

- **Credential-existence leakage via error identity**: per the Global Constraints, unknown-
  email and wrong-password must produce indistinguishable errors. A test that only checks
  "throws `InvalidCredentialsError`" for each case separately does NOT prove they're
  indistinguishable if the error's `.message` differs between the two call sites — the owning
  task's test must assert the exact same message string (or no distinguishing information)
  for both.
- **Session cap race/off-by-one at the eviction boundary**: the cap algorithm evicts the
  oldest session only when count >= cap BEFORE creating the new one — a test seeding exactly
  `MAX_CONCURRENT_SESSIONS_PER_COMPANY` existing sessions (not one fewer, not one more) is the
  one case most likely to reveal an off-by-one (evicting when it shouldn't, or failing to
  evict when it should). The task owning this logic must test exactly at the boundary, not
  only comfortably above or below it.
- **Expired session treated as absent, not as an error**: `validateSession()` on a token whose
  `Session` row exists but has `expiresAt` in the past must return `null`, the same as a
  token matching no row at all — a test asserting only "returns null for an unknown token"
  does not prove the expired-but-present case is handled, since a bug that only checks
  existence (not expiry) would pass that weaker test.
- **Rate limiter must key on email, not on any other value, and must not block a DIFFERENT
  email during another email's lockout** — a test with two distinct emails, one of which gets
  locked out, asserting the OTHER email can still log in normally in the same test run, is the
  one case that would catch a limiter accidentally keyed globally instead of per-email.
- **`SuperAdminSession` must be a genuinely separate table from `Session`**, not a reused or
  aliased relation — the migration task's own validation step must confirm the new table
  exists independently (not just that the schema validates), since a subtle mis-copy during
  the Prisma schema edit (e.g. accidentally relating to `CompanyUser` instead of `SuperAdmin`)
  would still pass `prisma validate` if the types happened to align, but would be a real
  correctness bug only a live query against the actual new table would catch.

// packages/auth/src/password.ts
import bcrypt from 'bcrypt';

const BCRYPT_COST_FACTOR = 12;

export async function hashPassword(plainPassword: string): Promise<string> {
  return bcrypt.hash(plainPassword, BCRYPT_COST_FACTOR);
}

export async function verifyPassword(plainPassword: string, hash: string): Promise<boolean> {
  return bcrypt.compare(plainPassword, hash);
}

// packages/auth/src/rate-limit.ts

interface FailureRecord {
  count: number;
  windowStart: number;
}

export class RateLimiter {
  private readonly failures = new Map<string, FailureRecord>();

  constructor(
    private readonly maxAttempts: number,
    private readonly windowMs: number,
  ) {}

  recordFailure(key: string): void {
    const now = Date.now();
    const existing = this.failures.get(key);
    if (existing && now - existing.windowStart < this.windowMs) {
      existing.count += 1;
    } else {
      this.failures.set(key, { count: 1, windowStart: now });
    }
  }

  isLocked(key: string): boolean {
    const existing = this.failures.get(key);
    if (!existing) return false;
    if (Date.now() - existing.windowStart >= this.windowMs) return false;
    return existing.count >= this.maxAttempts;
  }

  clear(key: string): void {
    this.failures.delete(key);
  }
}
```

// packages/auth/src/company-session.ts
import { db } from '@dossipv/db';
import { verifyPassword } from './password';
import { generateToken, hashToken } from './tokens';
import { RateLimiter } from './rate-limit';

export const SESSION_LIFETIME_MS = 30 * 24 * 60 * 60 * 1000; // 30 days
export const MAX_CONCURRENT_SESSIONS_PER_COMPANY = 3;
const RATE_LIMIT_MAX_ATTEMPTS = 10;
const RATE_LIMIT_WINDOW_MS = 15 * 60 * 1000; // 15 minutes

const loginRateLimiter = new RateLimiter(RATE_LIMIT_MAX_ATTEMPTS, RATE_LIMIT_WINDOW_MS);

export class InvalidCredentialsError extends Error {
  constructor() {
    super('Invalid email or password.');
    this.name = 'InvalidCredentialsError';
  }
}

export class TooManyAttemptsError extends Error {
  constructor() {
    super('Too many failed login attempts. Try again later.');
    this.name = 'TooManyAttemptsError';
  }
}

export interface AuthenticatedCompanyUser {
  id: string;
  companyId: string;
  email: string;
  fullName: string;
  role: 'OWNER' | 'MEMBER';
}

export interface LoginResult {
  user: AuthenticatedCompanyUser;
  token: string;
}

export async function login(email: string, plainPassword: string): Promise<LoginResult> {
  if (loginRateLimiter.isLocked(email)) {
    throw new TooManyAttemptsError();
  }

  const user = await db.companyUser.findUnique({ where: { email } });
  if (!user) {
    loginRateLimiter.recordFailure(email);
    throw new InvalidCredentialsError();
  }

  const passwordMatches = await verifyPassword(plainPassword, user.passwordHash);
  if (!passwordMatches) {
    loginRateLimiter.recordFailure(email);
    throw new InvalidCredentialsError();
  }

  loginRateLimiter.clear(email);

  const activeSessionCount = await db.session.count({
    where: { companyUser: { companyId: user.companyId }, expiresAt: { gt: new Date() } },
  });

  if (activeSessionCount >= MAX_CONCURRENT_SESSIONS_PER_COMPANY) {
    const oldest = await db.session.findFirst({
      where: { companyUser: { companyId: user.companyId }, expiresAt: { gt: new Date() } },
      orderBy: { createdAt: 'asc' },
    });
    if (oldest) {
      await db.session.delete({ where: { id: oldest.id } });
    }
  }

  const rawToken = generateToken();
  await db.session.create({
    data: {
      companyUserId: user.id,
      tokenHash: hashToken(rawToken),
      expiresAt: new Date(Date.now() + SESSION_LIFETIME_MS),
    },
  });

  return {
    user: { id: user.id, companyId: user.companyId, email: user.email, fullName: user.fullName, role: user.role },
    token: rawToken,
  };
}

export async function logout(rawToken: string): Promise<void> {
  await db.session.deleteMany({ where: { tokenHash: hashToken(rawToken) } });
}

export async function validateSession(rawToken: string): Promise<AuthenticatedCompanyUser | null> {
  const session = await db.session.findUnique({
    where: { tokenHash: hashToken(rawToken) },
    include: { companyUser: true },
  });

  if (!session || session.expiresAt <= new Date()) {
    return null;
  }

  await db.session.update({ where: { id: session.id }, data: { lastSeenAt: new Date() } });

  const user = session.companyUser;
  return { id: user.id, companyId: user.companyId, email: user.email, fullName: user.fullName, role: user.role };
}
```
